## 需要の読み取りの前提と限界
足跡の中心は、AIの要求に載っているURLを読むこと。特に、AIが取りに来て無かったURL（404）を、需要の手がかりとして読む。
この前提の裏づけと、限界（2026-11-07 に、検索で調べた。原典は、一部しか開いていない）。

- 裏づけ（間接）: ChatGPT などのAIが、存在しないURLを作る（ハルシネーション）ことは、複数の調査で報告されている。
  Ahrefs（2025-09、1,600万URL）は、ChatGPT が引用したURLの1.01%が404、AI全体では Google 経由の2.87倍。SE Ranking は、ChatGPT の引用の1.22%が404。
  ただし、これは、利用者に見せたリンクの話で、サイトへの取得の話ではない。
- 取得側: OpenAI の文書では、ChatGPT-User は、利用者の操作で動く取得（自動巡回ではない）。実務者の報告には、ChatGPT-User が、存在しない商品URLに、
  短時間で多数の404を出した例がある（1サイトの事例）。「ChatGPT-User が URL を推測する」と、OpenAI や Cloudflare が述べた資料は、見つからなかった。
- 限界1: 名乗りは偽装できる。実務者の報告には、ChatGPT-User を名乗る失敗要求の多くが、秘密のファイルを探る走査だった例がある。
  足跡は、検証済みのAIの行だけを、需要に数える（nginx 形式のログは、検証の可否が不明で、印を付けて数える）。
- 限界2: 404は、AIの推測だけでなく、古いリンクや、消したページでも出る。記録だけでは区別できない。
- 限界3: AIが取りに来た回数は、AIが回答に使った回数ではない。
- 作者（Kei）の発見として、「ChatGPT が、存在しないURLを作って取りに来る」ことを、自分のサーバーのログで見つけた、という観察がある（実サイトの数字は、書かない）。

## 目的
サイトのサーバー/CDNログを読み、AIクローラーとAI回答エンジンがそのサイトを
どう使っているかを調べ、次に作るべきページと直すべきページを、下書きつきで日本語で示す。
ログはAIが訪ねて来た足跡。AIに見つけてもらうための道しるべ、という位置づけ。

- テーマ: 「本来、誰にでも届くべきものを。」
- ユーザー: エンジニアもコンサルもいない小さな事業者（宿、商店、自治体サイト）。
- 配点: インパクト30 / デモ25 / Claudeの使い方25 / 深さ・実行力20。
- 回避: 汎用的なもの（基本RAG、Streamlitアプリ等）。

## 差別化
- AI回答の引用を数えるツール（Profound, Peec, Otterly等）は別のデータ源。
- ログ/クローラーツール（JetOctopus, Botify, Cloudflare AI Crawl Control等）は
  「誰がどのページに来たか」を既に出す。ダッシュボードだけでは差にならない。
- 最も近いのはSitelineの公開Claudeスキル（技術者向け）。日本語のAIクローラーログ解析ツールは見つからなかった。
- 差別化点: 判断（「無視してよい」を含む）、根拠の行つきの下書き、人の承認、平易な日本語。
  ダッシュボードは手段であって製品ではない。
- 取り入れる: ボット検証（UAは偽装できる）、前後比較。
  目安: AIボットのリクエストの10〜15%超が200以外なら要確認。
- 他の参加者の「店舗の導線台帳」は人の導線が対象。ashiatoはAIが来る入口。
  デモで旅館を使う場合は、「宿の在庫管理」を扱う他参加者とかぶらない設定にする（別業種も検討）。

## 入力
- URLとログ。Cloudflare Logpush NDJSONを主とし、nginx/Apacheのアクセスログも読む。
- 使うフィールド: EdgeStartTimestamp, ClientRequestURI, EdgeResponseStatus,
  ClientRequestUserAgent, ClientRequestReferer。IP・Cookieは使わない。
- 追加候補: Looker Studio連携、他のサーバーログ、コンテンツ生成、エージェント。

### ボット検証の手がかり（2026-11-02 に公式ドキュメントで確認）
出典: [Logpush http_requests フィールド](https://developers.cloudflare.com/logs/reference/log-fields/zone/http_requests/)、
[Verified bot categories](https://developers.cloudflare.com/bots/reference/verified-bot-categories/)、
[Verified bots](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/)。

- 使うフィールドは全部ある。バイト数は `EdgeResponseBytes`、パスだけなら `ClientRequestPath`。
- 検証の手がかりは `VerifiedBotCategory`（文字列）。特別な契約条件は書かれていない。
- `BotScore` `BotTags` `JA4` などは Bot Management 契約者のみ。小さな事業者は使えない前提で、頼らない。
- 値: `AI Crawler`（学習用）、`AI Assistant`（利用者の操作で動く）、`AI Search`（AI検索）、
  `Search Engine Crawler`（従来の検索）など。ただし、AIか検索かの区分としては当てにならなかった（下の「実サイトで見えたこと」）。
- Cloudflareは Web Bot Auth か IP検証でボットを検証する。UAだけでは検証されない。
- `AI Search` は 2026-07-01 以降、新しい検索クローラーは `Search` に分類され、互換のために残る。

**未確認:**
- 公式の値の一覧はWAFルール用。Cloudflare の GraphQL Analytics では `verifiedBotCategory` が取れることを実サイトで確認した。
  Logpush の出力に出る値は、Logpush のジョブを確認できていないため未確認。
- 「検証に失敗したUA偽装は `VerifiedBotCategory` が空になる」に公式の裏付けは無い。実サイトの集計では、
  検証済みにならない書式のGPTBotのUAは、常に空だった。

**仮定:** ボットの種類（学習／検索・回答／利用者の質問／従来の検索）は、UAの自前の表で決める。
`VerifiedBotCategory` が空でなければ「検証済み」、空なら「未検証」とし、未検証はAIの需要として数えない。
`VerifiedBotCategory` の値そのものは、AIか検索かの判定には使わない。
合成データの仕込み7（偽装スクレイパー）も、この仮定で作る。

### 実サイトで見えたこと（2026-11-03、実サイトの集計を確認。数字とサイト名は書かない）
ログの行は読んでいない。集計の傾向だけを、設計に反映する。

- **クロールは多いが、AI回答からの来訪はごくわずか。** 来訪の大半は従来の検索（Google、Bing）。
  デモの「読まれるのに来ない」の根拠にする。
- **AI回答からの来訪はクエリで見える。** `?utm_source=chatgpt...` が付く。
  リファラだけでなく `utm_source` も見る（処理の流れ 2 に反映）。
- **ページ以外が上位に来る。** 最も読まれたパスは `/_next/image`（画像）。API の通信が全体の大半。
  集計では資産パス（`/_next/image` `/cdn-cgi/` など）とAPIを分け、ページだけを話題にする。
- **UAの文字列だけでは、本物かどうか分からない。** GPTBot を名乗るUAには、括弧の位置やバージョンが違う変種が複数ある。
  検証済みになるのは `(KHTML, like Gecko; compatible; GPTBot/1.4; ...)` の書式だけで、`like Gecko);` の書式や
  他のバージョンは常に未検証だった（私の最初の推測は逆だった。2026-11-03 に訂正）。
  偽装の実例として合成データに入れ、UAの変種ごとの検証状況を集計に出す。
- **`VerifiedBotCategory` は、AIか検索かの判定に使えない。** OpenAI の検索ボット（OAI-SearchBot）は
  `Search Engine Crawler` に分類され、PerplexityBot は大半が未検証、ChatGPT-User は同じUA文字列が
  未検証と `AI Assistant` の両方に現れる。ボットの種類はUAの自前の表で決め、
  `VerifiedBotCategory` は「検証されたか」（空でないか）の印だけに使う。
- **`utm_source` 付きのリクエストの大半は、人の訪問ではない。** 403、エッジからの取得、504、302 が多く、
  200で人らしい行は少数だった。「AIの回答から来たお客さん」は、200で人らしい行だけを数える。
  リファラは `utm_source` に比べて少ない。
- **AIボットのリクエストのうち、200以外は目安（10〜15%）の範囲内だった。**
  404 の最多は画像などの資産パスだった（集計で資産パスを分ける方針の裏付け）。
- **ページ全体に占めるAIボットの割合は小さい。** 合成データBでも、AIボットは少数派にする。
- **Cloudflareの画面は無料で「誰が何件」を出す。** 会社別のクロール数・来訪数は Pro で既に見られる。
  ashiato の価値は集計ではなく、判断・下書き・承認・平易な日本語にある（差別化の節と同じ結論）。
- Cloudflareの画面の分類は会社別（OpenAI、Apple など）。Logpush のジョブ設定は、トークンの権限エラーで確認できていない。

## 処理の流れ
1. 取り込み: どの形式でも、時刻・パス・ステータス・UA・リファラ・バイト数に揃える。
2. 分類: AI学習クローラー / AI検索・回答の取得 / 利用者の質問による取得 /
   従来の検索ボット / 人。AI回答から来た人はリファラと `utm_source`（例: `chatgpt`）で判定。
   種類はUAの自前の表で決める。AIボット行には検証済み/未検証のフラグ
   （`VerifiedBotCategory` が空でなければ検証済み）。未検証はAIの需要として数えない。
   `utm_source` 付きは、200で人らしい行だけを「AIの回答から来た人」と数える。
3. 計測: ページごとに、AI取得数（アクター別）、404・リダイレクトの無駄、取得頻度、
   取得されないページ、取得されても人が来ないページ。
4. サイトとの突き合わせ: URLを巡回してタイトル・見出し・サイトマップを取り、パスを話題に変える。
5. 助言（Claude）: 生ログではなく集計表から。書くべき記事、直すべきページ
   （ブロック、404、薄い、サイトマップに無い）、営業・働きかけの先。
6. 実行（Claude）: 下書きまで作る（新規記事、薄いページの書き直し、404へのリダイレクト案）。
   自動公開しない。人が承認する。
7. ダッシュボードとレポート（日本語）: アクター別のAI取得、AIが欲しがるページとエラー、
   AI回答から来た人、下書きの承認キュー。すべての助言が根拠の行を示す。

範囲外（1週間）: 複数ユーザーのアカウント、他人のログの保存、自動公開、定期監視。

## エージェントの設計
- 分担: コードがログ解析・UA分類・集計、Claudeが判断・下書き・根拠確認、人が承認。
  エージェントは生ログを読まない。
- ツール案: 集計取得、ページ別の行（根拠）、サイトの現在のページ取得、2期間の比較、
  サイトマップ/robots.txt、下書き保存（根拠の行IDが必須。無ければ拒否）。
  公開・削除・サイトへの書き込みはできない。
- 実行順: 集計を読んで無駄な需要の大きい順に並べる → 上位ごとにページと行を確認 →
  原因を判断（ページ欠落/リンク切れ/robotsのブロック/薄い/偽装ボット/無視してよいノイズ）→
  日本語で下書き → 下書きの主張を行と照合してから保存 → 価値の高い数件で止める。
- モデル案（要再検討）: 主ループ Sonnet 5.5 (`claude-sonnet-5-5`)、
  UA分類など大量処理 Haiku 5.5 (`claude-haiku-5-5`)。実行1回は1ドル未満の見込み。

### 方式（未決定。小さな検証を作ってから決める）
Managed Agents（ベータ、ヘッダ `managed-agents-2026-04-01`）を優先、代替はAgent SDK。
- B ファイル方式（優先）: 集計と行別ファイルをセッションにマウントし、エージェントが読んで
  下書きをファイルに書く。outcomes（`user.define_outcome`、rubric、`max_iterations`）の採点役が、
  根拠が実在する行を指しているか等を確認。
- A カスタムツール方式: データは自前バックエンドに残し、根拠チェックも自前。
- Bを試して、駄目ならAへ。
- どちらでも小さなバックエンドが必須（APIキー保管、ファイルのアップロード、予算つきセッション作成、
  イベントのブラウザ中継、下書きの回収、セッション削除）。

### 事実メモ
- セッションには `environment_id` が必要。`networking` を省くと無制限になるので `limited` を明示。
- 予算は作成時のみ: `{"type":"limit","max_list_cost":{"amount":"100","currency":"USD"}}`。
- 権限ポリシーはカスタムツールには効かない。承認キューは自前のUIで作る。
- セッション記録は削除するまで残る。ゼロデータ保持の対象外。実ログは絶対に入れない。削除前に成果物を取り出す。
- 削除はアイドル時のみ（先に `user.interrupt`）。
- Agent SDKはAPIキー認証のみ。Maxプランは開発用で、公開後のツール実行には使えない。

## 画面と日本語表現
読む人はログを開いたことがない事業者。
- 用語: 「AIが学習のために読みに来た」「AIが答えを探しに来た」「誰かのAIへの質問で読みに来た」
  「AIの回答から来たお客さん」「AIが探したのに、ページがなかった」。
  「ユーザーエージェント」「ステータスコード」は出さない。
- 画面:
  1. ログをドロップ（「ログの取り方がわからない」でCloudflareの短い手順）
  2. 読み込み中は一文（「AIが何回、どのページを読みに来たか数えています」）
  3. 全体: 上に3つの数字（AIが読みに来た回数 / 探したのにページがなかった回数 / AIの回答から来たお客さん）、
     下に「読まれている/ページがない/読まれていない」つきの一覧
  4. エージェントの作業: 手順が流れる。各手順が根拠の行にリンク。端末風にしない
  5. 承認キュー: 何が問題か、一行の理由、下書き、根拠。ボタンは「そのまま使う / 直す / 使わない」
  6. 前後比較: 修正後のログで2期間を並べる
- レポート: 日本語1枚、印刷可。「今わかったこと」「次にやること」（順位つき、下書きつき）「根拠」（行）。
